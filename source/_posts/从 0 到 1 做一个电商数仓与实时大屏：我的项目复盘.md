## 一、为什么做这个项目

做这个项目的初衷很直接：我不想只会“写几条 SQL”，而是希望完整走一遍真实的数据工程链路。

从原始数据接入，到数仓分层建模，再到调度、实时计算、可视化展示，最后可以拿出来做演示、做面试讲解、做开源沉淀。

我选用 Kaggle 的 Olist 电商数据集，原因有三点：

- 数据字段相对完整，适合做交易、用户、物流、品类等主题分析
- 业务语义比较贴近真实电商场景
- 公开数据，方便复现和分享

这不是“单点功能项目”，而是一个“端到端工程项目”：

`数据 -> 计算 -> 调度 -> 服务 -> 前端展示` 全链路打通。

## 二、项目目标与范围

### 目标

- 搭建离线数仓链路（ODS / DWD / DWS / ADS）
- 搭建实时链路（Kafka + Flink SQL）
- 提供后端查询接口与前端可视化大屏
- 形成可运行、可排障、可扩展的工程文档

### 范围

- 数据源：Kaggle Olist CSV
- 离线处理：HDFS + Hive + Spark on Hive
- 调度：Azkaban
- 实时处理：Kafka + Flink SQL
- 展示层：前后端联调数据大屏

## 三、整体架构设计（离线 + 实时双链路）

这个项目采用了“离线主干 + 实时补充”的设计思路：

- 离线链路负责“稳定、完整、可回溯”的核心指标
- 实时链路负责“分钟级更新”的动态趋势
- 前端统一展示，两类数据通过后端聚合接口输出

### 1）离线链路

- Olist 原始 CSV 入 HDFS
- 建 RAW/ODS 外部表，完成基础清洗与字段规范
- DWD 层进行业务事实建模（订单、支付、物流等）
- DWS 层做按主题汇总（日粒度用户、交易、物流域）
- ADS 层产出面向看板的宽表和指标查询结果
- Azkaban 编排整条 DAG，支持定时跑批与质量检查

### 2）实时链路

- 将支付相关变更事件回放至 Kafka
- Flink SQL 按 1 分钟窗口聚合交易指标
- 实时结果写入服务可读取的数据层
- 前端按固定周期轮询，展示实时趋势变化

## 四、分层建模思路：为什么要 ODS -> DWD -> DWS -> ADS

我在这个项目里最重视的是“可维护性”。

很多练习项目会直接从明细表写到大屏 SQL，短期快，长期一定崩。

### ODS

- 保留业务原貌，尽量少做语义改造
- 统一类型、空值、时间格式，做基础标准化

### DWD

- 以事实表为中心，明确交易域、用户域、物流域的边界
- 解决“同一指标多口径”的问题，保证口径可追溯

### DWS

- 面向主题做统计沉淀，尽量把复杂 SQL 前移
- 降低接口层查询成本，提升可复用性

### ADS

- 为“页面/接口”直接服务
- 追求查询快、字段清晰、改动可控

> 一句话总结：分层不是为了好看，是为了控制复杂度。

## 五、我遇到的真实问题，以及怎么解决

这部分是我觉得最有价值的地方，因为大多数能力都长在“排障过程”里。

### 1）首屏加载慢：进入页面要等很久

**挑战**

前端进入大屏后，多个图表同时请求离线聚合接口。离线查询依赖 Hive 聚合，首屏等待时间明显偏长，用户体验差。

**方案**

- 后端增加缓存与降级策略，减少重复计算
- 前端改为“关键指标优先加载 + 非关键模块异步补齐”
- 对慢接口设置超时与 fallback，避免页面一直阻塞在“加载中”

**结果**

- 首屏可见时间明显缩短
- 即使离线接口慢，页面仍可先显示部分数据
- 用户不再陷入“无响应等待”

### 2）接口偶发超时：出现“离线聚合接口慢，已降级加载”

**挑战**

高峰时段或冷启动时，离线接口超过阈值，导致前端触发降级提示。

**方案**

- 后端压缩查询路径，优先读取已汇总结果
- 明确超时阈值与重试策略，控制请求风暴
- 将慢查询从在线链路迁移到预计算链路

**结果**

- 接口波动收敛，异常可预期
- 降级从“故障表现”变成“可控机制”
- 整体稳定性提升

### 3）前端报错导致页面一直“数据加载中”

**挑战**

出现 `ReferenceError`（例如某格式化函数未定义），前端初始化流程中断，但界面只显示“加载中”。

**方案**

- 快速定位控制台报错位置，补齐缺失函数/引用
- 在页面加载逻辑中增加错误兜底，避免静默失败
- 明确资源 404 的影响范围，避免连锁报错

**结果**

- 页面恢复可用
- 问题可快速复现与修复
- 调试效率提升

### 4）可视化细节问题：中文化、排序、布局、图表缺失

**挑战**

- 图表 tooltip/图例有英文未本地化
- 时间轴排序混乱，影响趋势判断
- 某些图表（如漏斗）只显示标题不显示内容
- 布局与边框影响整体观感

**方案**

- 统一图表文案与 formatter，确保中文一致性
- 前端按时间字段排序后再渲染
- 检查图表容器高度与初始化时机，确保正确挂载
- 调整大屏布局，移除不必要视觉负担

**结果**

- 可视化可读性明显提升
- 业务人员更容易理解指标
- 页面更像“可演示系统”，而不是“开发中页面”

### 5）地图指标异常：区域 GMV 看起来全为 0

**挑战**

业务数据是巴西地区，但早期可视化底图和地理映射存在不匹配，导致展示异常或误导解读。

**方案**

- 统一地理维度口径（地区编码、命名、映射）
- 使用与数据语境一致的地图方案
- 对无匹配区域显示明确提示，避免误读为真实 0

**结果**

- 地图信息更加可信
- 业务解释成本下降
- 避免“看起来很炫但指标不真实”的展示问题

## 六、性能优化我重点做了什么

我把优化分成三层，不只盯一个点。

### 1）数据层

- 尽量让重计算前置到离线任务
- 减少在线接口临时大聚合
- 保持指标口径固定，避免接口层重复拼装

### 2）服务层

- 聚合结果缓存
- 慢接口超时与降级
- 接口拆分与并行返回，降低单点阻塞

### 3）前端层

- 首屏关键卡片优先
- 图表延迟初始化与异步刷新
- 异常兜底（失败提示而非无限 loading）

> 经验结论：性能优化不是“改一行代码”，而是“端到端路径缩短 + 峰值压力可控 + 用户感知优化”。

## 七、工程化与文档沉淀

这个项目我刻意强化了“工程习惯”，而不是一次性脚本：

- 分阶段文档（规划、实施、排障、部署）
- 调度与应急 runbook
- 实时执行与 QA 指南
- 前后端分目录维护，便于协作与扩展

我自己最满意的一点是：不仅项目能跑，而且别人能接手。

## 八、如果让我重做一遍，我会提前做的三件事

- 更早定义核心指标口径表，减少后期反复改 SQL
- 更早做前端错误监控和接口性能埋点
- 更早拆分“演示版链路”和“全量版链路”，方便快速验证与迭代

## 九、这个项目带给我的能力增长

- 能独立搭建离线数仓分层并落地调度
- 能把实时流和离线链路结合成一个完整产品
- 能处理“性能 + 稳定性 + 可视化体验”三类问题
- 能把技术实现沉淀为可复用文档和面试表达

## 十、结尾

这个项目对我来说，不只是“做了一个大屏”，而是一次完整的数据工程实战：

从数据治理到计算架构，从调度保障到页面呈现，从功能实现到问题闭环。

如果你也在做类似项目，我的建议是：

- 先打通主链路，再追求炫技
- 先保证稳定可解释，再追求复杂和高级

真正有价值的，不是截图，而是可复现、可维护、可讲清楚。
